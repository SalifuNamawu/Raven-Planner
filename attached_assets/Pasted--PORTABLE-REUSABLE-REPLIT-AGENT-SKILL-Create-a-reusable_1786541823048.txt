# PORTABLE — REUSABLE REPLIT AGENT SKILL

Create a reusable Replit Agent skill named `portable`.

## IMPORTANT

This is **NOT** a request to modify the current application.

Create a **REAL reusable Replit Agent skill** that can be discovered and invoked on future projects.

Before creating the skill:

1. Determine the current Replit Agent mechanism for reusable skills/instructions.
2. Store this skill in the correct location supported by the current Replit Agent environment.
3. Do not guess or hardcode an obsolete Replit skill path.
4. Verify that the resulting skill can actually be discovered and invoked.
5. Do not modify the current application except where strictly necessary to verify that the skill itself works.

---

# 1. SKILL NAME

`portable`

---

# 2. ARCHITECTURAL PRINCIPLE

The skill must enforce the following default architecture:

```text
REPLIT
Development environment
        ↓
GIT
Branches / commits
        ↓
GITHUB
Source control + source of truth
        ↓
VERCEL
Preview + Production deployments
        ↓
DNS
Custom domain
```

The application must **NOT** depend on Replit for production.

The fundamental rule is:

> Develop anywhere, own the source in GitHub, deploy independently to Vercel, and never allow Replit to become an accidental production dependency.

---

# 3. PRIMARY OBJECTIVE

When `portable` is invoked on a project, inspect the actual repository and enforce production portability.

The project should be capable of being:

1. Developed in Replit.
2. Reproduced from GitHub.
3. Deployed independently to Vercel.
4. Connected to a custom domain through DNS.
5. Built without Replit being present.
6. Operated without Replit being present.
7. Handed over to another developer or client without requiring the original Replit account.

Do not blindly transform projects.

First understand the existing architecture, then make the **smallest safe changes** required for portability.

---

# 4. EXECUTION MODES

Support two modes.

## NORMAL MODE

Invoked with:

```text
portable
```

or:

```text
Run the portable skill
```

Behavior:

* inspect
* audit
* fix safe portability problems
* validate
* document
* report

## AUDIT-ONLY MODE

Invoked with:

```text
portable audit
```

Behavior:

* inspect
* audit
* validate where non-destructive
* report

Do **NOT** modify application files in audit-only mode.

---

# 5. REPLIT IS DEVELOPMENT ONLY

Treat Replit as a development environment.

Replit-specific development tooling is allowed when useful, but it must not become required for:

* production builds
* production runtime
* production database
* production authentication
* production storage
* production email
* production networking
* production URLs
* production secrets
* production deployment

Do not introduce production dependencies on:

* Replit hosting
* Replit Database
* Replit Auth
* Replit Storage
* Replit-specific APIs
* Replit-specific URLs
* Replit-specific filesystem behavior
* Replit-only runtime services
* Replit-only environment variables

unless the user explicitly requests a Replit-specific production feature.

Before introducing any Replit-specific service, ask internally:

> Would this application still build and operate if Replit disappeared tomorrow?

If the answer is NO, use or recommend a portable alternative.

---

# 6. GITHUB IS THE SOURCE OF TRUTH

The complete application must be reproducible from the GitHub repository.

Do not depend on files, source code, generated assets, configuration, or application state that exists only inside Replit.

Ensure appropriate project files are committed, including where applicable:

* `package.json`
* package manager lockfile
* source code
* workspace configuration
* TypeScript configuration
* framework configuration
* build configuration
* required static assets
* database schema/migrations
* Vercel configuration when necessary
* deployment documentation

Never commit:

* passwords
* API keys
* access tokens
* private credentials
* production secrets
* `.env` files containing secrets

Environment variable **names** may be documented.

Secret **values** must not be committed.

---

# 7. REPRODUCIBLE TOOLCHAIN

Inspect the package/runtime configuration.

Determine:

* package manager
* package manager version where specified
* lockfile
* Node.js/runtime version
* workspace configuration
* install command
* build command

Inspect:

* `packageManager` in `package.json`
* `engines`
* `.nvmrc`
* `.node-version`
* npm lockfiles
* pnpm lockfiles
* Yarn lockfiles
* Bun lockfiles
* workspace configuration

Detect conflicting package manager configuration.

Examples:

* multiple unrelated lockfiles
* `packageManager` declaring pnpm while npm lockfile is authoritative
* Replit using a global package unavailable during a clean install
* undeclared build tools
* globally installed CLI dependencies

The objective is:

> A fresh environment must be able to determine how to install and build the project from the repository itself.

Do not change package managers unnecessarily.

Preserve the project's existing package manager when valid.

---

# 8. CLEAN-ROOM REPRODUCIBILITY

Do not assume that a successful build inside the current Replit workspace proves portability.

Where safe and practical, validate the project as though it were freshly cloned.

Check for hidden dependencies on:

* existing `node_modules`
* stale build output
* generated but uncommitted files
* Replit caches
* global packages
* Replit secrets
* Replit environment variables
* untracked source files
* local configuration
* persistent filesystem state

A project should not pass portability validation merely because the current Replit workspace contains state that GitHub does not.

Do not destroy important local files while testing.

Use non-destructive clean-room validation whenever possible.

---

# 9. VERCEL IS THE DEFAULT PRODUCTION TARGET

Unless the user specifies another production platform, treat Vercel as the intended production platform.

The application should support, where applicable:

* Local Development
* Preview deployments
* Production deployments
* GitHub integration
* environment variables
* custom domains
* Vercel-compatible compute
* Vercel Functions where appropriate
* static deployment where appropriate
* framework-native Vercel deployment where appropriate

Do not assume that all Vercel applications must be converted into traditional serverless functions.

Determine the actual framework and backend architecture first.

---

# 10. PORTABILITY AND VERCEL DEPLOYABILITY ARE DIFFERENT

Evaluate these separately.

A project may be portable while still requiring architectural work before it can run correctly on Vercel.

Never damage an otherwise portable application merely to force a Vercel deployment.

Report two independent statuses:

```text
PORTABILITY STATUS
```

and:

```text
VERCEL DEPLOYABILITY
```

Possible portability results:

```text
PASS
PASS WITH WARNINGS
FAIL
```

Possible Vercel deployability results:

```text
READY
READY WITH CONFIGURATION
BLOCKED
```

If blocked, identify the exact reason and recommend the smallest safe architectural change.

---

# 11. GITHUB → VERCEL WORKFLOW

Design projects around this workflow:

```text
Replit
   ↓
Git branch
   ↓
GitHub
   ↓
Vercel Preview
   ↓
Testing / QA
   ↓
Pull Request / Review
   ↓
Merge to production branch
   ↓
Vercel Production
   ↓
Custom Domain
```

Do not design normal production workflows that require manually pushing directly from Replit into production.

Production should normally originate from the GitHub production branch.

---

# 12. PREVIEW VS PRODUCTION

Respect Vercel's deployment environments.

Non-production branches should normally generate Preview deployments.

The configured production branch should generate Production deployments.

Do not:

* hardcode production deployment URLs
* assume every Vercel deployment is production
* use Preview URLs as permanent production API endpoints

Application configuration must distinguish, where necessary:

* Development
* Preview
* Production

---

# 13. ENVIRONMENT VARIABLES

Never assume Replit environment variables automatically exist on Vercel.

Never hardcode secrets.

Identify all environment variables required by the application.

For every variable, determine where possible:

## EXPOSURE

* Public/client-safe
* Server-only secret

## ENVIRONMENT

* Development
* Preview
* Production

## LIFECYCLE

* Build-time
* Runtime
* Both

Document variable **names only**.

Never expose actual secret values.

Production secrets should normally live in Vercel's environment configuration or the appropriate production service.

Do not place production secrets in GitHub source files.

Check for framework-specific public environment variable conventions.

Examples include variables intentionally exposed to browser bundles.

Never classify a variable as safe merely because it is called an environment variable.

---

# 14. PORTS

Never make production code depend on a hardcoded Replit port.

Development servers may use:

```javascript
process.env.PORT
```

when appropriate.

Production configuration must follow the target platform's runtime behavior.

Do not make a frontend production build fail merely because `PORT` is unavailable.

Search for:

* hardcoded development ports
* Replit ports
* localhost URLs
* assumptions that backend services always listen on a manually selected port

Distinguish legitimate development configuration from production dependencies.

---

# 15. BASE PATHS AND URLs

Never require a Replit-specific `BASE_PATH`.

If the application requires a base path, provide a safe platform-independent default.

Production builds must succeed without Replit environment variables.

Do not hardcode:

* Replit domains
* Replit deployment URLs
* localhost production URLs
* Vercel Preview URLs as permanent production URLs

Use configuration/environment variables when environment-specific URLs are actually required.

---

# 16. REPLIT PLUGINS

Replit plugins may be used during development if they improve developer experience.

Examples include:

```text
@replit/*
@replit/vite-plugin-*
```

However:

* they must not be required for production unless explicitly intended
* production builds must work without Replit
* development-only plugins should be conditionally loaded when appropriate
* development tooling and production runtime dependencies must remain clearly separated

Do not blindly remove Replit packages.

First determine why each dependency exists.

---

# 17. DATABASE

Do not automatically introduce Replit Database.

Use the project's existing database when it is already appropriate and portable.

Prefer standard, portable database technologies where a new database is required.

Examples include:

* PostgreSQL
* Neon
* Supabase
* other standard PostgreSQL providers
* portable ORM/database abstractions

Database credentials must be environment variables.

Database code should not depend on Replit-specific runtime behavior.

Check whether database migrations/schema required for reproduction are committed.

Do not migrate an existing database provider merely for stylistic reasons.

---

# 18. FILE UPLOADS AND STORAGE

Do not assume the production filesystem is persistent.

For persistent user-generated files, use an appropriate persistent storage service.

Keep storage logic reasonably portable when practical.

Never store important customer files only in:

* Replit filesystem
* temporary server filesystem
* ephemeral Vercel runtime filesystem

Identify whether filesystem usage is:

* temporary
* build-time
* cache
* persistent application data

Only persistent application data requires durable storage.

---

# 19. EMAIL

Email functionality must use a portable implementation.

Acceptable examples include:

* SMTP
* Resend
* SendGrid
* Postmark
* other standard transactional email APIs

Do not depend on Replit-only email functionality.

Email credentials must remain server-side.

Do not expose transactional email credentials to frontend code.

---

# 20. AUTHENTICATION

Inspect authentication separately.

Identify whether authentication depends on:

* Replit Auth
* framework-native auth
* OAuth providers
* external identity providers
* database-backed sessions
* cookies
* server memory

Production authentication must not require Replit unless explicitly requested.

Check that session/state architecture is compatible with the intended production environment.

Do not replace working portable authentication unnecessarily.

---

# 21. API AND BACKEND

Inspect the actual backend architecture before modifying anything.

Possible architectures include:

* Express
* Node.js
* Next.js
* framework API routes
* Vercel Functions
* serverless APIs
* standalone API services
* external backend services

Do not assume:

```text
Express = incompatible with Vercel
```

First determine whether the existing backend can deploy using Vercel's currently supported runtime/framework model.

For backend code:

* do not assume a permanently running Replit process
* do not hardcode Replit URLs
* do not hardcode production ports
* use environment variables for environment-specific API endpoints
* keep frontend/backend communication portable
* identify state stored only in process memory
* identify background processes or long-running workloads that may not fit the intended platform

If an actual incompatibility exists:

1. Explain the incompatibility.
2. Identify the affected functionality.
3. Recommend the smallest safe architectural change.
4. Do not rewrite the entire backend unless genuinely required.

---

# 22. BACKGROUND JOBS AND LONG-RUNNING PROCESSES

Inspect for workloads that assume a permanently running machine.

Examples:

* infinite workers
* persistent WebSocket servers
* in-memory queues
* long-running cron processes
* local schedulers
* daemon processes
* background consumers

Do not automatically rewrite them.

Determine whether they are compatible with the intended Vercel architecture.

If not, report the issue and recommend an appropriate portable service or architecture.

---

# 23. MONOREPOS

If the repository is a monorepo:

1. Identify all applications.
2. Identify shared packages.
3. Identify workspace tooling.
4. Identify the intended production application or applications.
5. Determine the appropriate Vercel Root Directory for each deployable application.
6. Ensure build commands work from the selected context.
7. Preserve workspace dependencies.
8. Do not assume repository root equals frontend root.
9. Do not force a particular monorepo structure.

Valid deployments may use:

* an application-specific Root Directory
* repository root with workspace-filtered build commands

Choose based on the actual repository.

Document the required Vercel configuration.

---

# 24. FRAMEWORK DETECTION

Inspect the repository before deciding:

* framework
* package manager
* package manager version
* build command
* output directory
* Root Directory
* runtime/Node version
* API architecture
* frontend architecture

Do not blindly configure a project as:

* Next.js
* React
* Vite
* Express
* static HTML

Determine the actual architecture from repository evidence.

---

# 25. VERCEL CONFIGURATION

Prefer Vercel's automatic framework detection when it correctly represents the project.

Do not create `vercel.json` automatically.

Create it only when necessary.

If `vercel.json` is required:

* keep it minimal
* document why it exists
* avoid duplicating configuration Vercel can infer
* avoid obsolete Vercel configuration patterns

Inspect existing Vercel configuration before replacing it.

---

# 26. `.vercel` DIRECTORY

Inspect the local `.vercel` directory if present.

Treat it as local Vercel project linkage/configuration rather than application source unless current Vercel behavior explicitly requires otherwise.

Do not make application reproducibility depend on one developer's local `.vercel` state.

Check whether `.vercel` is appropriately ignored by Git where applicable.

Do not expose project/account metadata unnecessarily.

# 27. PORTABILITY AUDIT

Whenever the skill is invoked, scan the repository for portability risks.

Search for:

```text
@replit/*
REPL_ID
REPLIT_*

replit.dev
Replit APIs
Replit Database
Replit Auth
Replit Storage
hardcoded Replit domains
hardcoded localhost production URLs
hardcoded ports
filesystem persistence assumptions
development-only dependencies used in production
production dependencies on development tooling
.env files
secrets
API keys
private tokens
uncommitted required files
global package assumptions
generated-but-uncommitted required files
in-memory production state
background processes
environment-specific hardcoded URLs
```

Report each relevant issue.

Do not report harmless matches without understanding context.

---

# 28. SEVERITY CLASSIFICATION

Classify findings as:

```text
CRITICAL
HIGH
MEDIUM
LOW
INFO
```

Use approximately:

## CRITICAL

Production cannot safely operate, secrets are exposed, or severe data/security risk exists.

## HIGH

Deployment/build is blocked or production depends directly on Replit.

## MEDIUM

Portability or reproducibility is impaired but deployment may still work.

## LOW

Minor portability/deployment hygiene issue.

## INFO

Relevant architecture/configuration information that is not itself a problem.

---

# 29. DO NOT BREAK THE APPLICATION

Portability does not mean blindly deleting Replit dependencies.

Before modifying anything:

1. Understand why it exists.
2. Determine whether it is development-only or production-critical.
3. Determine whether it actually causes vendor lock-in.
4. Find a portable replacement if necessary.
5. Make the smallest safe change.
6. Validate the result.

Do not remove functionality merely to satisfy portability.

Do not perform unnecessary framework migrations.

Do not rewrite working architecture simply because another architecture is more familiar.

---

# 30. SAFE MODIFICATION POLICY

In NORMAL MODE, automatically fix issues only when the change is reasonably safe and its effect is understood.

For risky architectural changes:

1. Report the issue.
2. Explain the recommended change.
3. Avoid destructive modification unless clearly justified or explicitly authorized.

Examples of changes requiring extra caution:

* changing database providers
* replacing authentication
* restructuring backend architecture
* changing package managers
* changing frameworks
* deleting persistent data
* changing public API contracts
* replacing storage providers

---

# 31. VALIDATION

After portability changes, run the appropriate available checks.

Where applicable:

1. dependency installation
2. typecheck
3. lint
4. tests
5. production build

The project must successfully build without requiring a Replit-only runtime.

Do not report a missing test script as a failed test.

Use:

```text
PASS
FAIL
NOT AVAILABLE
NOT RUN
```

as appropriate.

---

# 32. VERCEL DRY RUN

If Vercel CLI is available and the project can be inspected safely, use a Vercel dry run where appropriate.

Prefer machine-readable output when useful:

```bash
vercel deploy --dry --format=json
```

or:

```bash
vercel deploy --dry
```

Use this to inspect what Vercel intends to deploy without intentionally creating a production deployment.

Do not treat inability to run the dry run as an application failure when:

* Vercel CLI is unavailable
* authentication is unavailable
* the project is not linked
* required account context is unavailable

Instead report:

```text
vercel dry-run: NOT RUN
```

with the reason.

Never create a production deployment merely to test portability unless explicitly requested.

# 34. CLIENT HANDOVER COMPATIBILITY

The application must be capable of being handed over to a client or another developer.

Do not make the agency's personal Replit account essential to production.

Production ownership should be separable and transferable.

Where applicable, ownership should be transferable for:

* GitHub repository
* Vercel project
* domain
* DNS
* database
* storage
* authentication provider
* transactional email
* analytics
* external APIs
* production secrets

The original developer or agency may remain an authorized collaborator without being a required production dependency.

# 39. SUCCESS CRITERIA

A project passes portability when all relevant conditions are satisfied:

* Replit is not required for production.
* GitHub contains the reproducible application source/configuration.
* Secrets are externalized.
* Production does not depend on Replit-only services.
* Package installation is reproducible.
* Build tooling is reproducible.
* Environment-specific configuration is externalized appropriately.
* Persistent data does not depend on ephemeral local filesystem state.
* Production services can be independently owned.
* The application can be handed over without requiring the original Replit account.

Vercel readiness additionally requires:

* compatible application architecture
* correct project/root detection
* valid build configuration
* appropriate environment configuration
* compatible backend/runtime behavior
* successful production build
* no known Vercel deployment blocker

# 40. IMPORTANT FINAL REQUIREMENTS

Do **NOT** merely create a Markdown document named `portable`.

Create a real reusable Replit Agent skill using the **currently supported Replit Agent skill/instruction mechanism**.

Do not assume a particular internal path if Replit's current environment uses another mechanism.

Verify:

1. where reusable skills currently belong
2. that `portable` is stored correctly
3. that Replit Agent can discover it
4. that `portable` can be invoked
5. that `portable audit` is understood as audit-only mode

Do not modify the current application merely to demonstrate portability.

The purpose of creating this skill is to make it reusable across future projects.

---

# FINAL PRINCIPLE

Always optimize for:

```text
DEVELOPMENT ENVIRONMENT != PRODUCTION DEPENDENCY
```

The desired architecture is:

```text
Develop in Replit
        ↓
Own the complete source in GitHub
        ↓
Preview and deploy through Vercel
        ↓
Route the custom domain through DNS
        ↓
Allow production ownership to be transferred
```

The ultimate test is:

> If Replit disappeared tomorrow, could this application still be cloned from GitHub, configured with its documented external services and environment variables, built, deployed, operated, and handed over?

If YES, the project is portable.

If NO, identify exactly why and remove or report the dependency using the smallest safe change.
