# OBJECTIVE

Refactor this repository into Raven Digital's standard production template.

Do **NOT** rewrite the application.

Do **NOT** redesign the UI.

Do **NOT** remove features.

Preserve the planner exactly as it works today.

The goal is to simplify the production architecture while keeping the user experience identical.

---

# CURRENT PROBLEM

The current repository is a Replit-generated pnpm workspace containing multiple applications.

The customer-facing application is relatively small, but the repository currently contains:

* multiple workspace packages
* a separate Express application
* shared libraries
* Replit-specific development tooling
* deployment complexity that is unnecessary for this project

This complexity is making deployment to Vercel unnecessarily difficult.

---

# TARGET ARCHITECTURE

The final production architecture should become:

```text
GitHub
    ↓
Vercel

├── React/Vite frontend
│
└── api/
      send-email.ts
      (Vercel Function)
```

There should be **one GitHub repository** and **one Vercel project**.

The planner should continue working exactly as before.

---

* planner workflow

Inspect the entire repository.

---

# STEP 2

Determine whether the current pnpm workspace is necessary.

If the workspace only exists because of the original Replit project structure:

Simplify it.

If shared packages are genuinely useful:

Preserve them.

---

# STEP 3

Inspect the Express backend.

Identify every route.

For each route determine whether it can become a Vercel Function.

If a route only:

* validates data
* sends email
* returns JSON

convert it into a Vercel Function.

Do not keep a permanent Express server unless it is actually required.

---

# STEP 4

Replace:

```
artifacts/api-server
```

with:

```
api/
```

using Vercel Functions.

The frontend should continue calling:

```
/api/send-email
```

without requiring a separate deployment.

---

# STEP 5

Inspect the email implementation.

Preserve all behaviour.

Move it into the Vercel Function.

Keep credentials in environment variables.

Do not expose secrets.

---

# STEP 6

Inspect the database package.

Determine whether it is actually required.

If the planner only emails submissions and does not store them:

Remove unnecessary production database dependencies.

Do not remove anything that is genuinely used.

---

# STEP 7

Remove unnecessary Replit production coupling.

Development tooling may remain.

Production must not depend on:

* Replit runtime
* Replit URLs
* REPL_ID
* REPLIT_*
* Replit-specific deployment behaviour

Conditional development plugins are acceptable.

The goal should resemble:

```

public/

package.json
```

Only keep a workspace if there is a genuine architectural reason.
